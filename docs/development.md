# Development configuration

Run scripts/prepare-development.sh once (it preserves existing credentials), start PostgreSQL with
`docker compose -p recipe-manager-dev -f deploy/compose.dev.yaml up -d db`, restore the pinned dotnet tool, then run
`scripts/run-api-development.sh migrate` and `scripts/run-api-development.sh run`. The API binds
https://localhost:7243. Configure/trust the normal ASP.NET Core development TLS certificate for your
own machine before browser use. The key-encryption certificate generated by the helper is separate
from TLS and must not be installed as a browser trust root.

All generated credentials and persisted key XML live under ignored deploy/secrets (0700 directory,
private files). Database password is read from its file. Data Protection keys are persisted and
encrypted using a password-protected PFX private key. Back up the database, key ring and encryption
certificate/password together. Do not regenerate an encryption certificate to fix a bad password:
old session/provider secrets would become unreadable. Production mounted paths use the same
Database:PasswordFile, DataProtection:KeysDirectory, CertificateFile and CertificatePasswordFile
configuration keys; the full deployment/backup drill is a later task.

The host refuses missing database credentials or unprotected persistent key configuration. Testing
and the framework OpenAPI mock entry point use ephemeral keys; neither contacts AI providers.
Structured request-failure logs contain only codes and trace IDs. EF parameter/detail logging and
routine request/query URL logs are disabled to avoid logging recipe input, credentials or tokens.
Do not enable sensitive data logging to diagnose a production recipe or account problem.

For local operator recovery, create a private 0700 runtime directory with a short path, export its
path as RECIPE_MANAGER_RUNTIME_DIR in both server and operator terminals, then use
`scripts/run-api-development.sh maintenance reset-password user@example.com`. The run helper enables
the same private listener on that directory and uses the generated ignored maintenance secret.
Without that variable, the extra listener is disabled. See docs/recovery.md for lifecycle and limits.

Run `scripts/run-web-development.sh` for the Angular client on https://localhost:4200. It exports the
normal ASP.NET development certificate into ignored private files and uses it for both the frontend
TLS listener and Node's additional CA trust for the backend proxy. Proxy TLS verification stays
enabled. Browser trust still requires your normal local certificate setup; the helper does not
change system trust. Secure cookies/CSRF use the web origin through this proxy, matching production
same-origin hosting. No credentials or certificate keys enter the browser bundle.

Private recipe images use Images:Directory, which must be a persistent directory outside wwwroot.
The development helper sets deploy/data/images (ignored by source control). The API accepts only
JPEG, PNG and WebP, up to 10 MiB and 20 megapixels. It applies phone-photo orientation, converts to
an sRGB raster and encodes a new static image without source metadata; animated inputs use their
first frame. Both clients must fetch images through the authenticated image endpoint. Never serve
the image directory using a static-file server. Include it in backups with the database.

File bytes are flushed before image metadata commits. A process/DB failure may leave a private
orphan file; retaining it is safer than deleting a file after an ambiguous successful commit.
Likewise a failed post-commit deletion can leave an inaccessible file. Operator repair may remove
files older than 24 hours only after verifying, against the current database, that their household
and storage-key pair has no ImageAssets row. Never delete files just because a live recipe does
not reference them: uploaded assets and cooking snapshots may still need them. Normal in-app
deletions check all registered references transactionally. Do not run storage repair during a
restore or while the database is unavailable.
